# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Avie — internal system for Fabiana Montemor's image/style consulting business. Covers the full business cycle: public lead capture via a diagnostic wizard, client CRM (Kanban), consultation scheduling, personalized report generation, and payment tracking. Deliberately minimal stack (no frontend build step, SQLite locally) so it can be maintained by non-developers.

## Commands

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env            # set a random SECRET_KEY

flask db upgrade                # apply migrations
flask create-admin              # create a staff user; prompts for role: owner | marketing
flask seed-demo-client          # optional: idempotent fictitious client (dossiê, reports, consultations, payments) for demoing the whole system
flask run                       # http://127.0.0.1:5000

pytest                          # run all tests
pytest tests/test_basic.py::test_name   # run a single test
```

After changing `models.py`, always generate a migration instead of hand-editing the DB:
```bash
flask db migrate -m "description"
flask db upgrade
```

There is no `pytest.ini`/`pyproject.toml` — pytest runs with defaults, all tests live in `tests/test_basic.py`. There is also no CI workflow — tests run manually. `.github/dependabot.yml` covers the one gap that's zero-effort to close without CI: weekly automated PRs for outdated/vulnerable `pip` dependencies (`requirements.txt`).

## Architecture

**App factory** (`app.py`): `create_app(config_class=Config)` builds the Flask app; a module-level `app = create_app()` exists for the gunicorn entrypoint (`app:app`, see `Procfile`). CLI commands (`create-admin`, `seed-admin`, `backup-db`) are registered via `register_cli(app)` inside the same file. `create-admin` (interactive) and `seed-admin` (non-interactive, reads `ADMIN_NAME`/`ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_ROLE` from env, idempotent, no-ops if the env vars are missing or the user already exists — used in production, see Deployment below) both set `User.role` to `owner` (full access, approves/publishes blog posts) or `marketing` (creates/edits blog posts, cannot approve).

**Extensions** (`extensions.py`): uninitialized instances (`db`, `login_manager`, `migrate`, `limiter`, `mail`) created at import time, bound to the app in `create_app`. `limiter` uses in-memory storage — fine for the current single-process deploy; switch `storage_uri` to Redis if the app ever runs multiple instances.

**Config** (`config.py`): env-driven via `.env` (`python-dotenv`). `AVIE_ENV=production` requires `SECRET_KEY` (raises at import otherwise) and turns on `SESSION_COOKIE_SECURE`. `_normalize_database_url` rewrites `postgres://` → `postgresql://` for SQLAlchemy 2.x compat (Render/Heroku/Railway hand out the old scheme) — kept as an opt-in escape hatch even though production currently runs SQLite (see Deployment). SQLite is used unless `DATABASE_URL` is set. `TestConfig` uses in-memory SQLite and disables CSRF/rate limiting.

**Blueprints** (`blueprints/`), all registered in `create_app`:
- `public` — landing (`/`), diagnostic wizard (`/diagnostico`), partial-lead capture (`/diagnostico/lead-parcial`), public blog (`/blog`, `/blog/<slug>`). Has a `before_request` hook that captures `utm_*`/`gclid`/`fbclid` into the session on first touch, applied to `Client` on any subsequent form submit (`_apply_utm`).
- `auth` — login/logout.
- `dashboard` — `/painel` Kanban overview.
- `clients` — client CRUD, status transitions, consultations, payments, all under `/painel/clientes`.
- `reports` — personalized report drafting/sending.
- `blog` — blog post drafting/review/publish under `/painel/blog` (see below).
- `ebooks` — lead-magnet CRUD under `/painel/ebooks` (see below).
- `client_area` — the client's own self-service portal under `/minha-area` (see "Two kinds of login" below).

**Models** (`models.py`): `User` (role: `owner`/`marketing`), `Client` (+ `utm_source/medium/campaign/content/term` attribution fields), `StyleProfile`, `Consultation`, `StyleReport`, `Payment`, `BlogPost`, `Ebook`. Status/choice constants (`CLIENT_STATUSES`, `BLOG_POST_STATUSES`, `LEAD_SOURCES`, etc.) live here and are injected into every template via the `inject_globals` context processor in `app.py`, along with a `label_for(choices, key)` helper.

**Two kinds of login, one `/login` form**: `User` (staff) and `Client` both implement Flask-Login's `UserMixin` and can authenticate — they share the single `/login` route (`blueprints/auth.py`), disambiguated by a prefix in `get_id()` (`"user-{id}"` vs `"client-{id}"`, parsed back apart in `app.py`'s `user_loader`). `login()` tries `User` first, then falls back to `Client` (only succeeds if a staff member has set `Client.password_hash` — see below). Post-login redirect and which navbar renders (`templates/base.html`) both branch on the `is_staff` property (`True` on `User`, `False` on `Client`) rather than `isinstance` checks in templates. **Every internal blueprint** (`dashboard`, `clients`, `reports`, `blog`, `ebooks`) registers `blueprints.auth.require_staff` as a `before_request` hook — this is the actual access-control boundary (not just `@login_required`, which a logged-in `Client` would also satisfy): it 403s any authenticated non-`User`. `client_area_bp` has the mirror-image guard (`require_client`, only in `blueprints/client_area.py`) so a `Client` can only ever reach their own data — the routes don't take a client_id param at all, they just read `current_user`.

**Client portal** (`/minha-area`, `blueprints/client_area.py` + `templates/client_area.html`): read-only self-service view of a client's own `StyleProfile` (diagnostic answers) and sent `StyleReport`s (`status="enviado"`). No self-registration — a staff member sets (or clears) `Client.password_hash` from the client's "Dados pessoais" page (`client_dados_pessoais.html`, `clients.set_client_password`/`remove_client_password`) and relays the password out-of-band (WhatsApp/e-mail), or uses the dossiê onboarding flow below, which handles this automatically. `Client.last_login_at` is updated on every client login; the *previous* value is stashed in `session["client_previous_login_at"]` right before overwriting, feeding the home page's one-line banner (see below) — this is a lightweight stand-in for the fuller multi-entry access history the owner asked for, deliberately not built yet (needs a real spec: how many entries, what counts as an "access," etc.). "Dicas personalizadas" (personalized tips) mentioned in the same request is also not implemented — no content source for it exists yet.

**Client home is a summary, never a duplicate** (`client_area.index`, `client_area.html`): after a UX review found the home page duplicating full content that a click away already showed it in full, the home page was cut down to a banner line (next consultation date > "you have news since your last visit" — computed by comparing `previous_login` against `StyleReport.sent_at`/`Look.created_at` > the plain last-access/first-access message, in that priority order) plus the 4 journey cards, each with a **real, data-driven one-line summary** instead of the old static description (e.g. "Outono suave · Elegante contemporâneo" instead of a canned sentence) — computed inline in the template from data already on `current_user`, not in `journey.py` (which stays a pure status calculator, untouched by this). Every card now navigates to its own page — no exceptions, no content duplicated inline on the home page itself:
- **Diagnóstico** → `client_area.diagnostico`/`client_area_diagnostico.html` (moved here verbatim from the old home page): `StyleAssessment` summary, then `StyleProfile` **or** the dossiê service cards (mutually exclusive, same as before), then "Recomendações da consultoria" (`other_reports`, most recent first — free, since `Client.reports` is already ordered by `created_at.desc()`).
- **Looks** → `client_area.looks`/`client_area_looks.html`, retitled "Minha assinatura visual" — originally **expanded to also show Closet and Personal Shopper inline** (`closet_items`/`shopping_list_items`, both read-only) as one long narrative page; later split into its own hub-of-cards architecture, see "Minha assinatura visual becomes a hub" below for the current shape.
- **Evolução** → new `client_area.evolucao`/`client_area_evolucao.html`: next consultation + history of past ones (filtered out of `current_user.consultations`, which is already ordered `scheduled_at.desc()`, so no re-sort needed).
- **Identidade** → unchanged.

One deliberate non-change: the "Diagnóstico" journey-card badge can legitimately read "Não iniciado" while its subtitle says "Dossiê disponível pra consulta" — `journey.py`'s `diagnostico_status` intentionally only signals off `StyleAssessment` (see `test_build_journey_dossie_no_longer_proxies_identity_or_diagnostico`, a PR4-era decision that a dossiê must never proxy for a different step's status), so a dossiê-onboarded client with no `StyleAssessment` yet shows exactly that combination. The subtitle wording was chosen specifically to describe availability, not completion, so it doesn't read as contradicting the badge.

**Staff-side client hub** (`clients.detail`, `client_detail.html`): opening a client no longer lands on one long page with every card stacked — it's a hub with a header, a native `<details>/<summary>` "Gerenciar" disclosure (Editar dados, Contato via WhatsApp with a `wa.me` link prefilled from the client's own phone, atualizar status — no custom JS needed for the expand/collapse), and a grid of 6 "journey" cards mirroring the client-facing "Minha Jornada" concept: Diagnóstico, Dossiê, Looks, Closet, Personal Shopper, Dados pessoais. Each card shows a filled/pending indicator and a one-line summary, and opens its own page (`client_diagnostico.html`, `client_dossie.html`, `client_looks.html`, `client_closet.html`, `client_personal_shopper.html`, `client_dados_pessoais.html`, all sharing the `_client_subpage_header.html` back-link partial) with the exact content that used to live inline on the old single page. Every create/edit/delete route for these resources redirects back to its own page (e.g. creating a look lands back on `/looks`, not the hub). Consultas and Pagamentos stay directly on the hub — they're operational/financial data, not a step of the style journey.

**Estúdio/Negócio navbar — kept to what nothing else already covers**: after the client hub above absorbed Sessões/Dossiê/Pagamentos into each client's own page, the old "Dossiês" cross-client list (Estúdio) added no function beyond browsing to a client that the "Clientes" search didn't already give, so it was removed outright (no replacement route). "Sessões" (Estúdio) was kept and relabeled **Agenda** — a cross-client "what's coming up this week" view is a real scheduling need with no other home — its route/blueprint (`sessions.list_sessions`, `/painel/sessoes/`) is unchanged, only the label and page heading changed. "Pagamentos" (Negócio) was kept as-is: cross-client payment reconciliation is a genuine bookkeeping task distinct from checking one client's own payments. Analytics (Negócio) dropped its "Clientes por estágio" breakdown, which was a second copy of the same counts already visible on the Painel Kanban's column badges — it now shows only what appears nowhere else (revenue, leads by source, recorrência).

**Client onboarding with dossiê** (`/painel/clientes/novo-com-dossie`, `ClientDossieForm` in `forms.py`, `clients.new_client_with_dossie`): consolidated flow for real-world clients who already received their dossiê outside the system, before Avie existed. One submission: upserts `Client` by email (creates if new, else updates name/phone on the existing record — never touches `source`/UTM attribution on an existing lead), sets `Client.status = "cliente_concluido"` (a client arriving with a finished dossiê has already been through diagnostic + consultoria, unlike `"cliente_ativo"` which implies an engagement still in progress), and upserts (not always-inserts — see `Client.dossie_report` below) a `StyleReport` with `status="enviado"`/`sent_at=now` from the submitted dossiê title, an optional `pdf_url` (external link to the original PDF, same no-upload pattern as `Ebook.file_url`), and up to five per-service fields — `estilo_pessoal`, `proporcoes`, `coloracao`, `visagismo`, `arquetipos` (each optional, at least one required). The column names predate the brand settling on final service naming; the labels actually shown everywhere are **Estilo / Biotipo / Cores / Visagismo / Arquétipos** (`blueprints/client_area.py:DOSSIE_SERVICE_LABELS`, and hardcoded in the templates/forms that touch these fields). `StyleReport.content` is auto-derived by concatenating whichever services are filled, purely so the older single-block report views (`report_view.html`) keep working. The route also generates a random temporary password (`secrets.token_urlsafe`, set via `Client.set_password` so the account is never passwordless) and a **password-reset token** (`Client.password_reset_token`/`password_reset_expires_at`, 72h validity, `generate_password_reset_token`/`password_reset_token_valid`/`clear_password_reset_token` methods) — this is the "esqueci minha senha" mechanism the client-portal note above says didn't exist yet. The reset link (`auth.reset_password`, public route, no `@login_required`) is sent via `emails.send_client_access_email` (same `MAIL_SERVER`-gated no-op pattern as everywhere else) and shown on a confirmation page (`client_dossie_success.html`) alongside a `wa.me` link built from the **client's own phone number** (normalized to digits, `55` country code prepended if missing — `clients._whatsapp_link`) with the message pre-filled, so staff can click-to-send it — this is a different `wa.me` usage than the business's own number (`config.WHATSAPP_NUMBER`) used elsewhere for inbound leads. `auth.reset_password` validates the token, logs out any current session, and lets the client set their own final password via `ResetPasswordForm`, clearing the token on success.

**One dossiê per client, editable in place** (`StyleReport.is_dossie` property — true if any of the 5 service fields is set; `Client.dossie_report` — the most recent report where `is_dossie` is true; `Client.other_reports` — everything else): `new_client_with_dossie` upserts onto `Client.dossie_report` instead of always creating a new `StyleReport`, so there's exactly one dossiê row per client and both the admin's "Dossiê" card (`client_dossie.html`, one of the journey cards linked from the client hub — see below) and the client-area service cards always read the exact same data — editing either side is impossible; there's only one edit path, `clients.edit_dossie` (`/painel/clientes/<id>/dossie/editar`, `EditDossieForm`, same 5 services + `pdf_url`, doesn't touch client identity/credentials unlike the onboarding route). `blueprints/reports.py`'s `edit_report`/`delete_report` redirect/400 on a dossiê-type report (`report.is_dossie`) rather than letting the generic `ReportForm` — which only has `title`/`content`/`status`, no service fields — silently desync the structured data from what the client-area cards show.

**"Diagnóstico preliminar" is a separate, narrower concept from the dossiê** (`reports.new_report`/`edit_report`/`delete_report`, the "Diagnóstico preliminar" card on `client_diagnostico.html`): this is specifically the auto-drafted report from `reports_engine.generate_report_draft(client, client.profile)`, built from the public wizard's `StyleProfile` — originally meant to help capture/nurture the lead, not to record delivered consulting services (that's the dossiê's job now). Its list only shows `client.other_reports` (dossiê-type reports are filtered out, so nothing shows twice), and each entry has its own Editar/Excluir actions.

The per-service fields exist so `client_area.diagnostico` (`blueprints/client_area.py`) can render a card per delivered service instead of the generic "Fazer meu diagnóstico" CTA — that CTA only makes sense for the public wizard funnel (`StyleProfile`, from `/diagnostico`), not for dossiê clients who already have their diagnostic embodied in the dossiê. `client_area_diagnostico.html` picks one of three states: `client.profile` (wizard diagnostic) → the original `dl` of answers; else non-empty dossiê service fields (`client.dossie_report`, one row now) → one card per service, each with a navy/gold circular icon badge (`.dossie-service-icon`, echoing the brand's Estilo/Biotipo/Cores/Visagismo/Arquétipos service badges) in a `.dossie-services-grid` (CSS grid, auto-fits 1–5 columns, equal-height rows); else → the CTA. The "Recomendações da consultoria" card only lists `other_reports` (same filter as the admin side), so a dossiê's content never shows twice (once as cards, once as a raw text block).

**Closet digital and style notes** (first module of the "Fase 2" Estúdio/Negócio rework — see `blueprints/clients.py:new_closet_item`/`delete_closet_item`, `ClosetItem` in `models.py`): staff-only CRUD, nested under a client like `Consultation`/`Payment` (`/painel/clientes/<id>/closet/novo`, create + delete only, no edit route — same minimal pattern as those two). Each `ClosetItem` is one wardrobe piece (`category` from `CLOSET_ITEM_CATEGORIES`, free-text `description`, optional `photo_url`, and optional `notes`), plus five preparatory columns from the "plataforma omnichannel" directive's Fase 3 — `cor`, `marca`, `ocasiao`, `estacao`, `estilo` (all nullable `String`, free text, no fixed choices) — added to the schema only, with **no form field or template display yet**, per that directive's explicit scope ("preparar... não tornar obrigatório... nenhuma tela nova"). The client sees her own closet read-only on `client_area_closet.html` (reached from "Minha assinatura visual", no edit/delete controls there) — this is deliberately view-only for now, a staff-curated deliverable rather than a client-editable inventory, per explicit decision when this was scoped. `Client.style_notes` is a separate free-text field from `Client.notes` (generic CRM notes) — specifically silhueta/formato do rosto/visagismo-type observations meant to inform closet curation and future "Criação de looks", edited via the same `ClientForm`/`client_form.html` as the rest of the client record, shown on the client's "Dados pessoais" page (`client_dados_pessoais.html`) but **not** exposed in `client_area` (staff-only, unlike the closet itself). Both are foundational pieces for "Lookbooks interativos"/"Closet Virtual" — the actual look-creation feature (staff assembles looks from these closet items; client views, doesn't build them, via `Look`/`LookItem`) already shipped as part of the MVP "Minha Imagem" journey.

**Looks organized by momento** (`Look.momento`, `LOOK_MOMENTS` in `models.py`): a fixed category (dia a dia / trabalho / fim de semana / evento especial / viagem), separate from the pre-existing free-text `ocasiao` — `momento` is the filterable bucket ("Trabalho"), `ocasiao` is the detail inside it ("Reunião com investidores"). Nullable column (looks created before this feature have no momento and just don't match any filter chip, rather than being hidden or breaking). `client_area.looks_gallery` accepts an optional `?momento=` query param and filters `current_user.looks` server-side — same nav-pills pattern already used by `sessions_list.html`/`payments_list.html` (a real link per option, full page reload, no JS) — with a "Todos" pill always showing the true total and per-momento pills only rendered for momentos that actually have at least one look (`momento_counts`). The one-line page summary at the top of "Minha assinatura visual" always reflects the **unfiltered** total, independent of whatever filter is active below it.

**Closet as an image-forward gallery** (`client_area_closet.html`, `blueprints/client_area.py:closet`): the front-2 follow-up to the momento work above — converted from a plain `<ul class="list-group">` text list to the same `<div class="row g-4">` photo-card grid already used for Looks (`item.photo_url` when present, no broken-image fallback rendered when it's not — the card just shows the category badge and description), plus category filter pills over the pre-existing `CLOSET_ITEM_CATEGORIES`, using the exact same nav-pills/query-param/full-reload pattern as the momento pills (`?categoria=`, `active_categoria`/`categoria_counts` computed in the route the same way as `active_momento`/`momento_counts`). Same care taken with the summary line: it reads `client.closet_items|length` (the true, unfiltered total), never the filtered `closet_items` passed to the template for rendering the grid — the same bug class already avoided for Looks. The "usada em N looks" cross-reference badge (PR62) and the graceful all-empty vs. filtered-empty states (PR63-style `{% elif client.closet_items %}` vs `{% else %}`) both carry over unchanged onto the new card markup.

**Image upload via Cloudinary** (`image_upload.py`, added when the "plataforma omnichannel" strategic directive reversed the earlier link-only decision): `upload_image(file_storage)` uploads to Cloudinary and returns the `secure_url`, or `None` if `CLOUDINARY_URL` isn't configured or the upload fails — same `MAIL_SERVER`-gated no-op pattern as `emails.py`, so the app works before/without a Cloudinary account. The highest-value photo fields (`Client.foto_perfil`, `Look.photo_url`, `ClosetItem.photo_url`, and `ShoppingListItem.photo_url` — added with the Personal Shopper deepening below) got a second, optional `FileField` alongside their existing `StringField` link (e.g. `ClientForm.foto_perfil_arquivo`) — if a file is submitted, its uploaded URL **overrides** whatever was pasted in the link field; if no file is submitted, the pasted link is used exactly as before, so nothing about the pre-existing external-link workflow broke. `StyleReport.pdf_url`, `Ebook.file_url`, and `BlogPost.cover_image_url` were deliberately **not** migrated (smaller blast radius, per the architecture review) — those three still only accept an external link.

**Personal Shopper** (`ShoppingListItem` in `models.py`, direct companion to the closet above, same data shape and same `CLOSET_ITEM_CATEGORIES`): staff-curated purchase recommendations, meant to stop the client from buying the wrong thing or overbuying. Originally shipped as "Lista de compras" with a boolean `purchased`; renamed at the product level after the "Minha Imagem" strategic directive reframed it explicitly as curation, not a marketplace — code identifiers and routes (`/painel/clientes/<id>/lista-compras/...`) were deliberately **not** renamed to keep the diff small, only the model shape and UI copy changed. `status` (`PERSONAL_SHOPPER_STATUSES`: `recomendada`/`aprovada`/`comprada`/`incorporada`) replaced `purchased`, set via `set_shopping_list_item_status` (`POST /lista-compras/<item_id>/status`, staff can jump to any stage freely, no enforced order) — a migration backfilled existing `purchased` values (`True`→`comprada`, `False`→`recomendada`). `motivo` (why the piece is recommended — the actual curatorial value) was added alongside the pre-existing `notes`.

**Personal Shopper deepened into three client-facing options** (explicit follow-up instruction that **partially reverses** the "no `link_compra`/loja/preço" decision above — `loja`/`preço` remain deliberately out of scope, only a purchase link was requested): `ShoppingListItem.link_compra` (external partner link, optional) and `.photo_url` (optional, same Cloudinary/link pattern as Closet/Look) turn a curated recommendation into something the client can act on directly. `client_area_personal_shopper.html` now renders all three options the business asked for, distinguished purely by data already on the item (no new field needed to tell them apart): **(1)** curation only — no `link_compra` — same read-only card as before, just restyled into the photo-card grid shared with Looks/Closet; **(2)** curation + purchase link — `link_compra` set — adds a "Ver produto" link and, while `status == "recomendada"`, an **"Aceitar recomendação"** button, the client's first-ever write action in this section (`client_area.accept_shopping_list_item`, `POST /minha-area/lista-compras/<item_id>/aceitar`, filters strictly by `current_user.id` like `toggle_look_favorite` — never takes a `client_id`) that moves the item to the pre-existing `"aprovada"` status rather than inventing a new one; **(3)** **Shopping Day** — a static CTA card (not tied to any `ShoppingListItem`) offering a paid in-person shopping session with Fabiana, via a `wa.me` link to **`config.WHATSAPP_NUMBER`** (the business's own number, same pattern as `landing.html`/`ebook_success.html` — deliberately not `clients._whatsapp_link`, which is for the client's own number) with a prefilled request message; staff schedules it like any other consultation by adding the new `CONSULTATION_TYPES` entry `("shopping_day", "Shopping Day")` (plain list entry, no migration) via the existing `clients.new_consultation` flow, and it then shows up automatically on `client_area.evolucao` and gets billed through the existing `Payment` model — zero new models for this third option. Staff-side, `client_personal_shopper.html` shows the photo/link/edit affordances plus a **"Notificar por WhatsApp"** button (only rendered when `link_compra` is set) that opens a `wa.me` chat to the **client's own number** (`_whatsapp_link`, unlike the Shopping Day CTA above) with the link pre-filled, so the consultant can proactively flag a new purchase recommendation instead of waiting for the client to notice it in her area — still no automated send, same manual-click pattern as the rest of the app. `clients.edit_shopping_list_item` (`/lista-compras/<item_id>/editar`) is the first edit route this model has ever had (previously create/status/delete only).

**"Minha assinatura visual" becomes a hub of cards** (`client_area.looks`/`client_area_looks.html`, `blueprints/client_area.py`): explicit follow-up instruction, with a visual reference, that **reverses** the "client-side they're one destination" call documented earlier in this file for Looks/Closet/Personal Shopper — the single narrative page (summary line + 3 stacked sections) became a 3-card navigation hub, one tap per section, matching a screenshot the business supplied. Rather than invent new visual language, this reuses the `.journey-grid`/`.journey-card`/`.journey-card-status.is-filled` CSS **already shipped for the staff-side client hub** (`client_detail.html`, see above) verbatim — same checkmark-badge/icon-circle/title/subtitle card shape, zero new CSS, so the client-facing hub and the staff-facing hub now share one pattern instead of two. `client_area.looks` (route unchanged, still what the home page's "Looks" journey card links to) now only renders the summary line plus the 3 cards; the content that used to live inline moved out to dedicated routes/templates, each with its own back-link to the hub:
- `client_area.looks_gallery` (`/minha-area/looks/galeria`, `client_area_looks_gallery.html`) — the momento-filterable look grid + favoritar, unchanged behavior from "Looks organized by momento" above, just relocated.
- `client_area.closet` (`/minha-area/closet`, `client_area_closet.html`) — the categoria-filterable closet grid, same filtering/summary logic as "Closet as an image-forward gallery" above, but the cards themselves got denser per a second reference screenshot: `col-6` instead of `col-md-6` so mobile shows **2 columns** (not 1 full-width column per item), and a plain "Sem foto" placeholder box (`aspect-ratio: 3/4`) replaces the old no-badge-at-all fallback when `photo_url` is empty, so the grid keeps its rhythm even for items without a photo yet.
- `client_area.personal_shopper` (`/minha-area/personal-shopper`, `client_area_personal_shopper.html`) — the 3-option Personal Shopper cards + Shopping Day CTA, unchanged behavior from "Personal Shopper deepened" above, just relocated.

`toggle_look_favorite` and `accept_shopping_list_item` redirect to `client_area.looks_gallery`/`client_area.personal_shopper` respectively (their own page), not back to the hub — so the write action's result is visible immediately without an extra tap. Each card's one-line subtitle and status checkmark (`is-filled` when the client has at least one look/peça/sugestão) are computed the same way the old inline section headers were, just now living on the hub instead.

**Blog system**: content-marketing funnel — articles are drafted/tested on `/blog` before being manually reused on LinkedIn. `blueprints/blog.py` implements a draft → review → publish flow: `rascunho` (draft, editable) → `em_revisao` (submitted) → `publicado` (live at `/blog/<slug>`, listed at `/blog`) or bounced back to `rascunho` with a `review_note`. Only `owner` can approve/reject/unpublish (`owner_required` decorator in `blueprints/blog.py`). `BlogPost.body_markdown` is authored as Markdown and rendered to HTML via the `markdown` Jinja filter (`blog_engine.render_markdown`, registered in `create_app`) — trusted staff-authored content, not sanitized beyond what the `markdown` library does by default (same trust level as other staff-supplied external URLs, e.g. `Ebook.file_url`). `blog_engine.format_date_pt` (Jinja filter `pt_date`) formats dates in Portuguese month names, since `strftime('%B')` depends on the server locale (renders in English in production). `templates/blog_post.html` is shared between the public route and the `owner_required`-free `blog.preview` admin route (`preview=True` flag). Cover images are external URLs (same ephemeral-disk reasoning as Ebook, see below) and back `og:image` per post (`base.html`'s `{% block og_image %}`) for LinkedIn share previews. **Blog posts are subject to the same ephemeral-disk data loss as everything else** (see Deployment) — unlike ad-hoc CRM records, published articles are a real content investment, so this is worth reconsidering once the blog has real posts worth keeping.

**Ebook (lead magnet)**: `Ebook` has no approval workflow (unlike BlogPost) — any logged-in staff creates/edits it directly under `/painel/ebooks`; `blueprints/ebooks.py`'s `activate_ebook`/`new_ebook`/`edit_ebook` enforce "only one `active=True` at a time" by flipping all others off before setting the new one. `file_url` is **always an external link** (Google Drive, Dropbox, etc.), never an uploaded file — same ephemeral-disk reasoning as BlogPost images, but more critical here since a broken file would silently 404 for anyone who already has the link. Public flow: `GET /ebook` shows the active ebook (or a graceful placeholder if none is active — no 404) with `EbookDownloadForm`; `POST /ebook` upserts a `Client` (by email, `source="ebook"` only if the client is new — never overwrites an existing lead's original attribution), appends a note recording the download and the `wants_diagnostic` opt-in, sends the link via `emails.send_ebook_email` (same MAIL_SERVER-gated no-op pattern as `send_diagnostic_confirmation`), then redirects to `/ebook/obrigado`, which shows the download link immediately (doesn't depend on email deliverability) plus a `wa.me` link so the lead can self-initiate a WhatsApp chat — there is no automated outbound WhatsApp send, that would require a paid WhatsApp Business API not currently integrated.

**Reports** (`reports_engine.py`): `generate_report_draft(client, profile)` builds a first-pass report text from the diagnostic answers; the consultant always reviews/edits before sending. No AI/external service involved by design — the roadmap in README.md notes this as a future integration point.

**Email** (`emails.py`): `send_diagnostic_confirmation` no-ops (logs only) when `MAIL_SERVER` isn't configured, so the public form keeps working before an email provider is set up.

**Deployment**: Render.com. The web service (`avie-app`) runs on the **free plan, zero cost** — deliberate choice while the site is experimental (see `render.yaml`). Production currently still runs SQLite on the free plan's **ephemeral** disk — `instance/avie.db` is wiped on every deploy and on restarts after idle spin-down, so there is no real data persistence right now; don't add features that assume production data survives across deploys without flagging that limitation. `startCommand` (`flask db upgrade && flask seed-admin && flask seed-demo-client && gunicorn app:app --bind 0.0.0.0:$PORT`) re-applies migrations, recreates the admin user from `ADMIN_*` env vars, and recreates the fictitious demo client (`seed-demo-client`, no env vars needed, always runs) on every boot, so the site is always usable again after a data wipe without a manual step. The web service (`avie-app`) was created manually, so it does **not** auto-apply `render.yaml` — its settings (plan, build/start command, env vars) must be kept in sync by hand in the Render dashboard; a `startCommand`/env var change in this file only takes effect in production once someone pastes the equivalent change into the dashboard too. `.python-version` pins `3.11.9` (Render's default can be much newer and has broken `psycopg2-binary` wheels before).

**Postgres migration (decided, not yet provisioned)**: the business chose Render's own managed Postgres (not a third-party free tier like Supabase/Neon) to replace the ephemeral SQLite — `render.yaml` declares a `databases: avie-db` (plan `starter`, so it has a real monthly cost) and wires the web service's `DATABASE_URL` to it via `fromDatabase`. `config.py`'s `_normalize_database_url` (rewrites the `postgres://` scheme Render hands out to `postgresql://` for SQLAlchemy 2.x) and `psycopg2-binary` in `requirements.txt` were already in place before this decision — validated end-to-end against a real local Postgres 16 instance (full migration chain from scratch, seeds, writes through the `Look`↔`ClosetItem` relationship, the computed Jornada) with **zero code changes required**. What's still needed, and can't be done from here: actually provisioning `avie-db` in the Render dashboard (or applying this Blueprint), which starts the monthly cost.

## Frontend

No build step: Bootstrap, fonts, and the brand mark are vendored under `static/` (no CDN — the app must keep working if a visitor's network blocks Google Fonts/jsDelivr). Brand color tokens are CSS variables in `static/css/style.css`; typography in `static/css/fonts.css`. Templates extend `templates/base.html` (Jinja); form fields render via the `render_field` macro in `templates/_formhelpers.html`. The navbar's "Recursos" dropdown (Bootstrap dropdown, custom-styled dark to match the navy navbar — see `.navbar .dropdown-menu`/`.dropdown-item` in `style.css`) links to Blog and Ebook; it's duplicated with different hrefs between the authenticated branch (`blog.list_posts`/`ebooks.list_ebooks`, the admin panels) and the public `{% else %}` branch (`public.blog_index`/`public.ebook_landing`) in `base.html`.
