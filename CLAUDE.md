# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Avie — internal system for Fabiana Montemor's image/style consulting business. Covers the full business cycle: public lead capture via a diagnostic wizard, client CRM (Kanban), consultation scheduling, personalized report generation, and payment tracking. Deliberately minimal stack (no frontend build step, SQLite locally) so it can be maintained by non-developers.

## Commands

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env            # set a random SECRET_KEY

flask db upgrade                # apply migrations
flask create-admin              # create a staff user; prompts for role: owner | marketing
flask seed-demo-client          # optional: idempotent fictitious client (dossiê, reports, consultations, payments) for demoing the whole system
flask run                       # http://127.0.0.1:5000

pytest                          # run all tests
pytest tests/test_basic.py::test_name   # run a single test
```

After changing `models.py`, always generate a migration instead of hand-editing the DB:
```bash
flask db migrate -m "description"
flask db upgrade
```

There is no `pytest.ini`/`pyproject.toml` — pytest runs with defaults, all tests live in `tests/test_basic.py`. There is also no CI workflow — tests run manually. `.github/dependabot.yml` covers the one gap that's zero-effort to close without CI: weekly automated PRs for outdated/vulnerable `pip` dependencies (`requirements.txt`).

## Architecture

**App factory** (`app.py`): `create_app(config_class=Config)` builds the Flask app; a module-level `app = create_app()` exists for the gunicorn entrypoint (`app:app`, see `Procfile`). CLI commands (`create-admin`, `seed-admin`, `backup-db`) are registered via `register_cli(app)` inside the same file. `create-admin` (interactive) and `seed-admin` (non-interactive, reads `ADMIN_NAME`/`ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_ROLE` from env, idempotent, no-ops if the env vars are missing or the user already exists — used in production, see Deployment below) both set `User.role` to `owner` (full access, approves/publishes blog posts) or `marketing` (creates/edits blog posts, cannot approve).

**Extensions** (`extensions.py`): uninitialized instances (`db`, `login_manager`, `migrate`, `limiter`, `mail`) created at import time, bound to the app in `create_app`. `limiter` uses in-memory storage — fine for the current single-process deploy; switch `storage_uri` to Redis if the app ever runs multiple instances.

**Config** (`config.py`): env-driven via `.env` (`python-dotenv`). `AVIE_ENV=production` requires `SECRET_KEY` (raises at import otherwise) and turns on `SESSION_COOKIE_SECURE`. `_normalize_database_url` rewrites `postgres://` → `postgresql://` for SQLAlchemy 2.x compat (Render/Heroku/Railway hand out the old scheme) — kept as an opt-in escape hatch even though production currently runs SQLite (see Deployment). SQLite is used unless `DATABASE_URL` is set. `TestConfig` uses in-memory SQLite and disables CSRF/rate limiting.

**Blueprints** (`blueprints/`), all registered in `create_app`:
- `public` — landing (`/`), diagnostic wizard (`/diagnostico`), partial-lead capture (`/diagnostico/lead-parcial`), public blog (`/blog`, `/blog/<slug>`). Has a `before_request` hook that captures `utm_*`/`gclid`/`fbclid` into the session on first touch, applied to `Client` on any subsequent form submit (`_apply_utm`).
- `auth` — login/logout.
- `dashboard` — `/painel` Kanban overview.
- `clients` — client CRUD, status transitions, consultations, payments, all under `/painel/clientes`.
- `reports` — personalized report drafting/sending.
- `blog` — blog post drafting/review/publish under `/painel/blog` (see below).
- `ebooks` — lead-magnet CRUD under `/painel/ebooks` (see below).
- `client_area` — the client's own self-service portal under `/minha-area` (see "Two kinds of login" below).

**Models** (`models.py`): `User` (role: `owner`/`marketing`), `Client` (+ `utm_source/medium/campaign/content/term` attribution fields), `StyleProfile`, `Consultation`, `StyleReport`, `Payment`, `BlogPost`, `Ebook`. Status/choice constants (`CLIENT_STATUSES`, `BLOG_POST_STATUSES`, `LEAD_SOURCES`, etc.) live here and are injected into every template via the `inject_globals` context processor in `app.py`, along with a `label_for(choices, key)` helper.

**Two kinds of login, one `/login` form**: `User` (staff) and `Client` both implement Flask-Login's `UserMixin` and can authenticate — they share the single `/login` route (`blueprints/auth.py`), disambiguated by a prefix in `get_id()` (`"user-{id}"` vs `"client-{id}"`, parsed back apart in `app.py`'s `user_loader`). `login()` tries `User` first, then falls back to `Client` (only succeeds if a staff member has set `Client.password_hash` — see below). Post-login redirect and which navbar renders (`templates/base.html`) both branch on the `is_staff` property (`True` on `User`, `False` on `Client`) rather than `isinstance` checks in templates. **Every internal blueprint** (`dashboard`, `clients`, `reports`, `blog`, `ebooks`) registers `blueprints.auth.require_staff` as a `before_request` hook — this is the actual access-control boundary (not just `@login_required`, which a logged-in `Client` would also satisfy): it 403s any authenticated non-`User`. `client_area_bp` has the mirror-image guard (`require_client`, only in `blueprints/client_area.py`) so a `Client` can only ever reach their own data — the routes don't take a client_id param at all, they just read `current_user`.

**Client portal** (`/minha-area`, `blueprints/client_area.py` + `templates/client_area.html`): read-only self-service view of a client's own `StyleProfile` (diagnostic answers) and sent `StyleReport`s (`status="enviado"`). No self-registration — a staff member sets (or clears) `Client.password_hash` from the client's "Dados pessoais" page (`client_dados_pessoais.html`, `clients.set_client_password`/`remove_client_password`) and relays the password out-of-band (WhatsApp/e-mail), or uses the dossiê onboarding flow below, which handles this automatically. `Client.last_login_at` is updated on every client login (still shown to staff on "Dados pessoais") — it no longer feeds anything client-facing, see "Home stripped to title + 4 cards, no banner" below for why. A fuller multi-entry access history the owner once asked for was never built (needs a real spec: how many entries, what counts as an "access," etc.), and is now even less likely to be, having lost its one client-facing use. "Dicas personalizadas" (personalized tips) mentioned in the same request is also not implemented — no content source for it exists yet.

**Client home is a summary, never a duplicate** (`client_area.index`, `client_area.html`): after a UX review found the home page duplicating full content that a click away already showed it in full, the home page was cut down to a greeting plus the 4 journey cards (see "Home stripped to title + 4 cards, no banner" below for how that greeting itself was later reduced to a single static line). Every card now navigates to its own page — no exceptions, no content duplicated inline on the home page itself:
- **Diagnóstico** → `client_area.diagnostico`/`client_area_diagnostico.html` (moved here verbatim from the old home page): `StyleAssessment` summary, then `StyleProfile` **or** the dossiê service cards (mutually exclusive, same as before), then "Recomendações da consultoria" (`other_reports`, most recent first — free, since `Client.reports` is already ordered by `created_at.desc()`).
- **Looks** → `client_area.looks`/`client_area_looks.html`, retitled "Minha assinatura visual" — originally **expanded to also show Closet and Personal Shopper inline** (`closet_items`/`shopping_list_items`, both read-only) as one long narrative page; later split into its own hub-of-cards architecture, see "Minha assinatura visual becomes a hub" below for the current shape.
- **Evolução** → new `client_area.evolucao`/`client_area_evolucao.html`: next consultation + history of past ones (filtered out of `current_user.consultations`, which is already ordered `scheduled_at.desc()`, so no re-sort needed).
- **Identidade** → unchanged.

**Home journey cards: icon-forward squares, no text subtitle** (`client_area.html`, `.home-journey-grid`/`.home-journey-card` in `style.css`, explicit follow-up with a visual reference): the 4 cards originally carried a colored text status badge ("Não iniciado"/"Em andamento"/"Concluído") plus a data-driven one-line subtitle (e.g. "Outono suave · Elegante contemporâneo") — on the request that redesigned "Minha assinatura visual" into a card hub (see below), the same instinct was applied here: strip the cards down to an icon (`_journey_home_icon.html`, a shared macro `journey_home_icon(key)` for the 4 concepts — `identidade`/`diagnostico`/`looks`/`evolucao`; the `diagnostico` and `looks` icons reuse the **exact same SVG paths** as the staff hub's `client_detail.html` journey-card icons, so the same concept looks identical on both sides), a bold centered title, and a small status indicator tucked in the top-right corner — no subtitle text at all anymore, no colored badge pill. The status indicator reuses `.journey-card-status`/`.is-filled` verbatim (third reuse of that component) plus a **new third visual state**, `.is-in-progress` (a small gold dot inside the circle, vs. empty for not-started and a gold-filled checkmark for done) — needed here specifically because, unlike the binary filled/empty hubs elsewhere, the home page's 4 steps have a genuine 3-value status (`journey.py`'s `nao_iniciado`/`em_andamento`/`concluido`) that a plain checkbox can't represent. The grid is a fixed 2 columns at every breakpoint (not `auto-fit` like the other hubs) with `aspect-ratio: 1` cards and a `max-width: 480px` cap on the grid itself — deliberately keeps the cards square-ish and prevents them from ballooning into oversized tiles on wide desktop screens, and on mobile all 4 fit on one screen with no scrolling, which was the actual complaint being fixed. The now-obsolete "Diagnóstico can show 'Não iniciado' with a dossiê-aware subtitle" nuance documented in earlier revisions of this file no longer applies — there's no subtitle to contradict the badge anymore — but the underlying `journey.py` decision it was protecting (a dossiê must never proxy for `diagnostico_status`, only `StyleAssessment` does — see `test_build_journey_dossie_no_longer_proxies_identity_or_diagnostico`) is untouched: a dossiê-onboarded client with no `StyleAssessment` yet still shows an empty (not-started) status dot on that card, by design.

**Home card names** (`journey.py`): a formal UX spec (explicit, numbered, in the style of a product brief) tightened the home, on the explicit principle "o recurso mais valioso da cliente é seu tempo e sua atenção." The 4 card titles were shortened to their possessive form — `journey.py`'s `title` values are **Minha Identidade / Meu Dossiê / Minha Assinatura Visual / Minha Evolução** (were "Conhecendo minha identidade" / "Meu diagnóstico de imagem" / "Minha assinatura visual" / "Minha evolução contínua") — only the 4 `journey.py` step titles changed; the destination pages' own headings (`client_area_diagnostico.html`, `client_area_evolucao.html`) still say the old names until their own modules get touched, a deliberately temporary inconsistency.

**Home stripped to title + 4 cards, no banner** (`client_area.html`, `client_area.index`, `blueprints/auth.py`): the same spec above also introduced a single computed "próximo passo" banner under "Olá, {nome}" — `_next_step(client, previous_login, journey)`, a ranked function picking at most one dynamic call-to-action (dossiê novo > looks novos > próxima consulta > identidade pendente), falling back to a plain last/first-access sentence. A direct follow-up request judged even that one line as clutter ("a tela ficou com rotas duplicadas," pointing at the redundant "Sua jornada"/"Sua jornada de transformação" pairing above the cards) and asked for something "direto e objetivo": nothing under the greeting except a single line — "Sua jornada de Transformação" — then straight into the 4 cards. Rather than leave the banner logic dead in place, it was removed outright along with everything that only existed to feed it: `_next_step` itself, the `previous_login`/`session.pop("client_previous_login_at", ...)` read in `client_area.index`, and the matching stash in `blueprints/auth.py`'s `login()` (previously saved the client's prior `last_login_at` into the session right before overwriting it, solely so the banner could show it once). `Client.last_login_at` itself is untouched — still updated on every client login and still shown to staff on "Dados pessoais" — only the client-facing "seu último acesso foi em..." sentence is gone. The 5 tests written for `_next_step`'s priority ordering were removed with it rather than kept skipped or repointed at dead code.

**That title line reuses the landing page's gold handwritten "brush" style** (`client_area.html`, `.lp-script-brush` in `style.css`): a follow-up request, with a reference image, asked for "Sua jornada de Transformação" to look as close as possible to that image — which turned out to be a screenshot of the landing page's own `.lp-script-brush` treatment ("Uma imagem estratégica, sem perder sua identidade.", `templates/landing.html`) almost verbatim, down to the wording rhythm. Rather than approximate it with a new style, the same class is reused as-is on `client_area.html` (`<p class="lp-script-brush" style="font-size: 1.8rem;">`, matching the smaller of the two landing-page usages) — "Caveat" bold cursive with the brand's metallic gold gradient clipped to the text (`background-clip: text`), replacing the earlier plain bold/`--avie-gold` treatment. Zero new CSS; this is the third place `.lp-script-brush` is used, all sharing one definition.

**Client area gets a sidebar shell; home becomes a dashboard (partially reverses "minimal home")** (`templates/client_area_base.html`, `templates/_client_sidebar.html`, `client_area.html`, `blueprints/client_area.py`): a later, explicit request supplied a dashboard-style visual reference (persistent left sidebar, home with quick-access icons + widget cards) and asked for the client area to adopt that shape, responsive on mobile and desktop. Every `client_area_*.html` template now extends `client_area_base.html` instead of `base.html` directly, filling `{% block client_content %}` instead of `{% block content %}` — the original top navbar from `base.html` is untouched (still has brand/"Sair"), `client_area_base.html` just adds a shell below it: a fixed dark sidebar on desktop (`.client-sidebar`, ≥768px) with the same nav destinations as the home's 4 journey cards (Início/Identidade/Dossiê/Assinatura Visual/Evolução), active-state highlighted via `request.endpoint`; on mobile the sidebar becomes a Bootstrap offcanvas (`bootstrap.bundle.min.js` already vendored, no new JS) behind a "Menu" toggle bar. `_client_sidebar.html` is a single include shared by both the fixed sidebar and the offcanvas body, so the nav markup exists in one place. The shell breaks out of `base.html`'s centered `.container` via the existing `.full-bleed` trick (same one used throughout `landing.html`) so the sidebar reaches the viewport edge.

The home page (`client_area.index`) keeps the exact same 4 journey cards markup (`.home-journey-grid`/`.home-journey-card`, `journey-card-status`/`is-filled`/`is-in-progress` — unchanged on purpose, `tests/test_basic.py` asserts on that exact HTML) — CSS only turns them into a 4-across row on desktop instead of a 2×2 square (scoped to `.client-home-quicklinks` so it doesn't touch the same component's reuse on the "Minha assinatura visual" hub or elsewhere). Below that, three widgets were added, each a deliberate adaptation of the reference to what Avie actually has rather than a literal copy:
- **"Conteúdos para você"** — the client's own blog feed, reusing the public `BlogPost` model (latest 4 `status="publicado"`, same source as `/blog`), each card linking to `public.blog_post`.
- **"Serviços do seu plano"** replaces the reference's progress-ring ("70% concluído"): Avie has no plan/subscription concept, so instead of a computed percentage it lists the 5 dossiê services (same `DOSSIE_SERVICE_LABELS`) with the same filled/empty `journey-card-status` badge used everywhere else in the app — "o que a cliente já consumiu" (which services her dossiê already covers), read directly off `client.dossie_report`, not a synthetic progress number.
- **"Seu próximo agendamento"** and, below it, a **daily inspirational quote** — the appointment card reuses the same next-consultation lookup as `client_area.evolucao` (factored out into `_next_consultation(client)` so both routes share one query instead of duplicating it); the quote comes from `DAILY_QUOTES`, a short fixed list in `blueprints/client_area.py` picked deterministically by day-of-year (`_quote_of_the_day`) — no new model, since 7 rotating phrases don't justify a table/CRUD yet.

This directly narrows the "Home stripped to title + 4 cards, no banner" decision documented above: the home page no longer stays deliberately empty below the cards — that minimalism held until a fresh explicit request (with its own visual reference) asked for a richer dashboard, and this is a newer, more specific instruction superseding the earlier one for this one screen.

**Staff-side client hub** (`clients.detail`, `client_detail.html`): opening a client no longer lands on one long page with every card stacked — it's a hub with a header, a native `<details>/<summary>` "Gerenciar" disclosure (Editar dados, Contato via WhatsApp with a `wa.me` link prefilled from the client's own phone, atualizar status — no custom JS needed for the expand/collapse), and a grid of 6 "journey" cards mirroring the client-facing "Minha Jornada" concept: Diagnóstico, Dossiê, Looks, Closet, Personal Shopper, Dados pessoais. Each card shows a filled/pending indicator and a one-line summary, and opens its own page (`client_diagnostico.html`, `client_dossie.html`, `client_looks.html`, `client_closet.html`, `client_personal_shopper.html`, `client_dados_pessoais.html`, all sharing the `_client_subpage_header.html` back-link partial) with the exact content that used to live inline on the old single page. Every create/edit/delete route for these resources redirects back to its own page (e.g. creating a look lands back on `/looks`, not the hub). Consultas and Pagamentos stay directly on the hub — they're operational/financial data, not a step of the style journey.

**Estúdio/Negócio navbar — kept to what nothing else already covers**: after the client hub above absorbed Sessões/Dossiê/Pagamentos into each client's own page, the old "Dossiês" cross-client list (Estúdio) added no function beyond browsing to a client that the "Clientes" search didn't already give, so it was removed outright (no replacement route). "Sessões" (Estúdio) was kept and relabeled **Agenda** — a cross-client "what's coming up this week" view is a real scheduling need with no other home — its route/blueprint (`sessions.list_sessions`, `/painel/sessoes/`) is unchanged, only the label and page heading changed. "Pagamentos" (Negócio) was kept as-is: cross-client payment reconciliation is a genuine bookkeeping task distinct from checking one client's own payments. Analytics (Negócio) dropped its "Clientes por estágio" breakdown, which was a second copy of the same counts already visible on the Painel Kanban's column badges — it now shows only what appears nowhere else (revenue, leads by source, recorrência).

**Client onboarding with dossiê** (`/painel/clientes/novo-com-dossie`, `ClientDossieForm` in `forms.py`, `clients.new_client_with_dossie`): consolidated flow for real-world clients who already received their dossiê outside the system, before Avie existed. One submission: upserts `Client` by email (creates if new, else updates name/phone on the existing record — never touches `source`/UTM attribution on an existing lead), sets `Client.status = "cliente_concluido"` (a client arriving with a finished dossiê has already been through diagnostic + consultoria, unlike `"cliente_ativo"` which implies an engagement still in progress), and upserts (not always-inserts — see `Client.dossie_report` below) a `StyleReport` with `status="enviado"`/`sent_at=now` from the submitted dossiê title, an optional `pdf_url` (external link to the original PDF, same no-upload pattern as `Ebook.file_url`), and up to five per-service fields — `estilo_pessoal`, `proporcoes`, `coloracao`, `visagismo`, `arquetipos` (each optional, at least one required). The column names predate the brand settling on final service naming; the labels actually shown everywhere are **Estilo / Biotipo / Cores / Visagismo / Arquétipos** (`blueprints/client_area.py:DOSSIE_SERVICE_LABELS`, and hardcoded in the templates/forms that touch these fields). `StyleReport.content` is auto-derived by concatenating whichever services are filled, purely so the older single-block report views (`report_view.html`) keep working. The route also generates a random temporary password (`secrets.token_urlsafe`, set via `Client.set_password` so the account is never passwordless) and a **password-reset token** (`Client.password_reset_token`/`password_reset_expires_at`, 72h validity, `generate_password_reset_token`/`password_reset_token_valid`/`clear_password_reset_token` methods) — this is the "esqueci minha senha" mechanism the client-portal note above says didn't exist yet. The reset link (`auth.reset_password`, public route, no `@login_required`) is sent via `emails.send_client_access_email` (same `MAIL_SERVER`-gated no-op pattern as everywhere else) and shown on a confirmation page (`client_dossie_success.html`) alongside a `wa.me` link built from the **client's own phone number** (normalized to digits, `55` country code prepended if missing — `clients._whatsapp_link`) with the message pre-filled, so staff can click-to-send it — this is a different `wa.me` usage than the business's own number (`config.WHATSAPP_NUMBER`) used elsewhere for inbound leads. `auth.reset_password` validates the token, logs out any current session, and lets the client set their own final password via `ResetPasswordForm`, clearing the token on success.

**One dossiê per client, editable in place** (`StyleReport.is_dossie` property — true if any of the 5 service fields is set; `Client.dossie_report` — the most recent report where `is_dossie` is true; `Client.other_reports` — everything else): `new_client_with_dossie` upserts onto `Client.dossie_report` instead of always creating a new `StyleReport`, so there's exactly one dossiê row per client and both the admin's "Dossiê" card (`client_dossie.html`, one of the journey cards linked from the client hub — see below) and the client-area service cards always read the exact same data — editing either side is impossible; there's only one edit path, `clients.edit_dossie` (`/painel/clientes/<id>/dossie/editar`, `EditDossieForm`, same 5 services + `pdf_url`, doesn't touch client identity/credentials unlike the onboarding route). `blueprints/reports.py`'s `edit_report`/`delete_report` redirect/400 on a dossiê-type report (`report.is_dossie`) rather than letting the generic `ReportForm` — which only has `title`/`content`/`status`, no service fields — silently desync the structured data from what the client-area cards show.

**"Diagnóstico preliminar" is a separate, narrower concept from the dossiê** (`reports.new_report`/`edit_report`/`delete_report`, the "Diagnóstico preliminar" card on `client_diagnostico.html`): this is specifically the auto-drafted report from `reports_engine.generate_report_draft(client, client.profile)`, built from the public wizard's `StyleProfile` — originally meant to help capture/nurture the lead, not to record delivered consulting services (that's the dossiê's job now). Its list only shows `client.other_reports` (dossiê-type reports are filtered out, so nothing shows twice), and each entry has its own Editar/Excluir actions.

The per-service fields exist so `client_area.diagnostico` (`blueprints/client_area.py`) can render a card per delivered service instead of the generic "Fazer meu diagnóstico" CTA — that CTA only makes sense for the public wizard funnel (`StyleProfile`, from `/diagnostico`), not for dossiê clients who already have their diagnostic embodied in the dossiê. `client_area_diagnostico.html` picks one of three states: `client.profile` (wizard diagnostic) → one collapsible card per question (see below, same treatment as the dossiê services); else non-empty dossiê service fields (`client.dossie_report`, one row now) → one card per service, each with a navy/gold circular icon badge (`.dossie-service-icon`, echoing the brand's Estilo/Biotipo/Coloração/Visagismo/Arquétipos service badges) in a `.dossie-services-grid` (CSS grid, auto-fits 1–5 columns, equal-height rows); else → the CTA. The "Recomendações da consultoria" card only lists `other_reports` (same filter as the admin side), so a dossiê's content never shows twice (once as cards, once as a raw text block). The dossiê service formerly labeled "Cores" is now **"Coloração"** everywhere it's user-facing (`DOSSIE_SERVICE_LABELS`, the dossiê form field, the landing page's service list, the staff coloração page) — the underlying column/URL segment (`coloracao`) and internal `icon_key` (`"cores"`) were **not** renamed, only the label a person reads.

**"Meu Dossiê" leads with a 3-item synthesis, not the full document** (`client_area_diagnostico.html`, `StyleAssessment.pontos_chave` in `models.py`): the same formal UX spec that produced the single home CTA above ("a cliente não deve precisar 'estudar' a tela") also asked that the dossiê module show a very short synthesis before the full collapsible content — "suficiente para consulta rápida," with the complete document existing "para aprofundamento." The synthesis (a single highlighted card, only rendered when `client.style_assessment` has at least one of the three pieces) is exactly 3 items, each optional and independently gated: **Minha essência** (`StyleAssessment.mensagem_desejada`, already existed, already short), **Minha paleta** (`StyleAssessment.estacao_cor` text, plus — new — the first `ColoracaoImage` of the dossiê if the consultant has uploaded any, shown as a small photo above the text), and **Pontos-chave** (`StyleAssessment.pontos_chave`, a **new** `Text` column — 2-3 short recommendations, one per line, edited by staff on the existing `style_assessment_form.html`, no new route). A "Ver dossiê completo" button anchor-links (`#dossie-completo`) down to the exact same collapsible content that already existed — nothing about the full-detail rendering changed, it just now sits below the synthesis instead of being the first thing on the page. Deliberate cut, called out here because it removes something previously shown: `paleta_principal`, `estilo_predominante`, and `estilo_complementar` — three more `StyleAssessment` fields that used to render in a plain `dl` above the dossiê content — are **no longer shown to the client** (the spec's synthesis only calls for 3 items, not 5); they're untouched in the database and still editable/visible to staff on `client_diagnostico.html`, just no longer surfaced client-side. The wizard-diagnostic path (`client.profile`) can show the exact same synthesis card too, since it keys off `StyleAssessment` independent of which diagnostic path the client came through — a dossiê and a public-wizard client are treated identically here.

**"Minha Evolução" leads with the consultant's own words, and trims the consultation list to a few** (`client_area_evolucao.html`, `blueprints/client_area.py:evolucao`, `Client.foco_atual` in `models.py`): third and final piece of the same formal UX spec — this module should answer "o que faço agora?", with "a presença humana... perceptível," not read like an agenda or a full history. `Client.foco_atual` is a **new** `Text` column — a short paragraph the consultant writes about where the client is right now in her journey (same authoring pattern as `identidade_rotina`/`objetivo`/`estilo`: staff-written narrative, not client input, edited on the same `ClientForm`/`client_form.html`, new "Minha evolução" section at the bottom). When set, it renders as the first thing on the page, attributed — "Agora na sua jornada" / the message / "— Fabiana" (the name is hardcoded, same as other places in the app that speak in her voice directly, e.g. the landing page). Below it, "Próximo encontro" is unchanged. **Long dossiê/report text collapses instead of forcing a long scroll** (`client_area_diagnostico.html`, `static/css/style.css`): on mobile, 4-5 dossiê service cards each holding a full paragraph — plus however many "Recomendações da consultoria" reports — meant a client had to scroll past several screens of text just to see what sections existed at all. **Staff-side dossiê is also a hub of cards, plus a coloração image carousel** (`client_dossie.html`, `blueprints/clients.py`, `ColoracaoImage` in `models.py`): the same button-card treatment given to "Minha assinatura visual" (see above) was extended to the dossiê's 5 services — `client_dossie.html` shows the dossiê header (title/sent date/PDF link) followed by a `.journey-grid` of 5 `.journey-card`s (Estilo/Biotipo/Cores/Visagismo/Arquétipos), same CSS reused a third time now, zero new styling. **Each dossiê service can break into sub-análises — `DossieSection`, collapse by default, tabs when comparable** (`models.py`, `blueprints/clients.py`, `blueprints/client_area.py:_dossie_services`/`_group_dossie_sections`, `client_area_diagnostico.html`): triggered by a real client dossiê in PDF form showing that each of the 5 services usually isn't one flat paragraph — Biotipo alone had "Análise de Proporções," "Peças que Favorecem," and "Peças a Evitar" as distinct parts, each with its own text and reference photos. A service with zero sections renders exactly as it always has; nothing about an existing dossiê changes in appearance.

**Collapse vs. tabs is a deliberate, evaluated choice, not a free-for-all**: an explicit review of the UI primitives already available (`<details>` collapse used everywhere in this app, Bootstrap tabs — zero new dependency since `bootstrap.bundle.min.js` is already vendored, sticky positioning, the carousel) concluded collapse should be the default for nearly everything (mobile-first, matches every other disclosure pattern in the app, no horizontal-overflow risk from long Portuguese labels), with tabs reserved for the one genuinely comparable case: 2+ sections sharing the same `group` (e.g. "Esportivo" and "Tradicional" under Estilo, `group="estilos_identificados"`). `_group_dossie_sections(sections)` in `blueprints/client_area.py` implements this: sections without a `group` each become their own `{"type": "collapse", "sections": [section]}` block; sections sharing a non-empty `group` collapse into one `{"type": "tabs", "sections": [...]}` block (first-appearance order preserved). `client_area_diagnostico.html` renders `collapse` blocks as nested `<details class="manage-disclosure">` (the same component used for "Recomendações da consultoria" and the staff "Gerenciar" box) and `tabs` blocks as plain Bootstrap `.nav-tabs`/`.tab-content` — the first time this app uses Bootstrap tabs, a deliberate one-off exception to the collapse-everywhere convention. Sticky positioning and a dossiê-wide table of contents were evaluated and explicitly **not** built — collapsed-by-default already avoids forcing a long scroll past unwanted content, so a fixed index would only pay for itself if real usage shows the full dossiê getting long enough to need one.

**Blog system**: content-marketing funnel — articles are drafted/tested on `/blog` before being manually reused on LinkedIn. `blueprints/blog.py` implements a draft → review → publish flow: `rascunho` (draft, editable) → `em_revisao` (submitted) → `publicado` (live at `/blog/<slug>`, listed at `/blog`) or bounced back to `rascunho` with a `review_note`. **Ebook (lead magnet)**: `Ebook` has no approval workflow (unlike BlogPost) — any logged-in staff creates/edits it directly under `/painel/ebooks`; `blueprints/ebooks.py`'s `activate_ebook`/`new_ebook`/`edit_ebook` enforce "only one `active=True` at a time" by flipping all others off before setting the new one. `file_url` is **always an external link** (Google Drive, Dropbox, etc.), never an uploaded file — same ephemeral-disk reasoning as BlogPost images, but more critical here since a broken file would silently 404 for anyone who already has the link. **Reports** (`reports_engine.py`): `generate_report_draft(client, profile)` builds a first-pass report text from the diagnostic answers; the consultant always reviews/edits before sending. No AI/external service involved by design — the roadmap in README.md notes this as a future integration point.

**Email** (`emails.py`): `send_diagnostic_confirmation` no-ops (logs only) when `MAIL_SERVER` isn't configured, so the public form keeps working before an email provider is set up.

**Deployment**: Render.com. The web service (`avie-app`) runs on the **free plan, zero cost** — deliberate choice while the site is experimental (see `render.yaml`). Production currently still runs SQLite on the free plan's **ephemeral** disk — `instance/avie.db` is wiped on every deploy and on restarts after idle spin-down, so there is no real data persistence right now; don't add features that assume production data survives across deploys without flagging that limitation. `startCommand` (`flask db upgrade && flask seed-admin && flask seed-demo-client && gunicorn app:app --bind 0.0.0.0:$PORT`) re-applies migrations, recreates the admin user from `ADMIN_*` env vars, and recreates the fictitious demo client (`seed-demo-client`, no env vars needed, always runs) on every boot, so the site is always usable again after a data wipe without a manual step. The web service (`avie-app`) was created manually, so it does **not** auto-apply `render.yaml` — its settings (plan, build/start command, env vars) must be kept in sync by hand in the Render dashboard; a `startCommand`/env var change in this file only takes effect in production once someone pastes the equivalent change into the dashboard too. `.python-version` pins `3.11.9` (Render's default can be much newer and has broken `psycopg2-binary` wheels before).

**Postgres migration (decided, not yet provisioned)**: the business chose Render's own managed Postgres (not a third-party free tier like Supabase/Neon) to replace the ephemeral SQLite — `render.yaml` declares a `databases: avie-db` (plan `starter`, so it has a real monthly cost) and wires the web service's `DATABASE_URL` to it via `fromDatabase`. `config.py`'s `_normalize_database_url` (rewrites the `postgres://` scheme Render hands out to `postgresql://` for SQLAlchemy 2.x) and `psycopg2-binary` in `requirements.txt` were already in place before this decision — validated end-to-end against a real local Postgres 16 instance (full migration chain from scratch, seeds, writes through the `Look`↔`ClosetItem` relationship, the computed Jornada) with **zero code changes required**. What's still needed, and can't be done from here: actually provisioning `avie-db` in the Render dashboard (or applying this Blueprint), which starts the monthly cost.

## Frontend

No build step: Bootstrap, fonts, and the brand mark are vendored under `static/` (no CDN — the app must keep working if a visitor's network blocks Google Fonts/jsDelivr). Brand color tokens are CSS variables in `static/css/style.css`; typography in `static/css/fonts.css`. Templates extend `templates/base.html` (Jinja); form fields render via the `render_field` macro in `templates/_formhelpers.html`. The "Recursos" dropdown (Bootstrap dropdown) links to Blog and Ebook; it's duplicated with different hrefs between the staff branch (`blog.list_posts`/`ebooks.list_ebooks`, the admin panels) and the public branch (`public.blog_index`/`public.ebook_landing`) in `base.html`.

**One header component, three branches, no hamburger anywhere** (`base.html`, `.pf-header` in `style.css`): `<body>` opens with a three-way `{% if current_user.is_authenticated and current_user.is_staff %}…{% elif current_user.is_authenticated %}…{% else %}…{% endif %}` at the top level, each branch rendering its own complete `<header class="pf-header">` — brand plus a `.pf-nav` whose *content* differs per branch, but the CSS component is exactly one, shared unmodified across all three. It started as the public/anonymous-only header, built for an explicit design brief (approved via an Artifact wireframe/proposal before implementation, see the session that added it): **no hamburger, at any width** — Diagnóstico/Recursos/Clientes stay visible always. One CSS breakpoint (`max-width: 1023.98px`) switches it from a single horizontal row (brand left, nav right, generous negative space, no dividers) to two stacked lines (brand line, then a full-width row where the items split the width evenly with faint dividers) — the 768–1023px range deliberately reuses the same two-line composition rather than getting a third tablet-specific layout. Below that, two more `@media` steps (400px, 330px) shrink spacing/type/icons further but never remove a label or let one wrap to two lines. Gold (`--avie-gold`) is reserved for state — `.is-active` (current page, set server-side by comparing `request.endpoint`), `:hover`, `:focus-visible` (with a visible outline), and the open `aria-expanded="true"` state on any item with a submenu (still Bootstrap's dropdown JS/`data-bs-toggle`, just restyled flat with no shadow via `.pf-header .dropdown-menu`) — never applied to the nav as a whole. The old mobile-only `.navbar-icon-links`/`.navbar-cta`/`.navbar-links-anon` CSS from the prior (hamburger-based) public-header iteration was deleted outright rather than left dead.

**Staff and client headers followed the same concept next, on request, once the public one was approved** (`base.html`): a follow-up explicitly asked for the staff/admin header and the client-area header to "seguir o mesmo conceito" as the just-shipped public `.pf-header` — both still ran the original Bootstrap `.navbar` (pill links, `navbar-toggler` hamburger, `.collapse`) at the time. Proposed first as an Artifact (reusing `.pf-header`'s exact CSS classes with each branch's own nav content, at 1440px and 390px) and approved before implementation, same two-step pattern as the public header. The staff branch (`current_user.is_staff`) now renders `.pf-nav` with 4 items — **Painel** (single link), **Estúdio** and **Negócio** (dropdowns, same `.pf-dropdown`/`.pf-menu`/`.pf-chev` markup "Recursos" uses on the public header, unmodified), and **Sair** (now a plain `.pf-item`, not the filled `.btn-brand` pill it used to be — consistent with no item on this header ever getting a solid fill) — each with its own icon (grid for Painel, briefcase for Estúdio, trending-line for Negócio, exit-arrow for Sair). The client (logged-in, non-staff) branch renders just 2 — **Minha área** (home icon, reused from `_client_sidebar.html`'s "Início") and **Sair** — the simplest instance of the component. `.is-active` on a dropdown trigger is computed by endpoint *prefix*, not exact match, since a dropdown covers several routes: `request.endpoint.startswith('clients.') or request.endpoint.startswith('sessions.')` lights up Estúdio, `payments.`/`analytics.`/`blog.`/`ebooks.` lights up Negócio (`{% set ep = request.endpoint or '' %}` guards the `None` case rather than calling `.startswith` on it directly). Zero new CSS beyond the 5 icons above and this endpoint-prefix logic — `.pf-header`/`.pf-inner`/`.pf-brand`/`.pf-nav`/`.pf-item`/`.pf-dropdown`/`.pf-menu`/`.pf-chev` are all reused verbatim from the public header, which is why the component-level comment above them in `style.css` no longer says "born for the public header, staff/client keep the old navbar" — it now documents the shared, three-branch shape directly. The now fully unused `.navbar`/`.navbar-brand`/`.navbar-brand-text/-name/-tagline`/`.navbar-links`/`.navbar-link-pill`/`.navbar .dropdown-menu`/`.navbar .btn-brand`/`.navbar-toggler`/`.navbar-collapse` CSS (nothing in any template references those classes anymore) and the `.brand-mark` image class were deleted outright rather than left dead. **Out of scope, deliberately**: the client area's own left sidebar (`client_area_base.html`/`_client_sidebar.html`, fixed on desktop, a Bootstrap offcanvas behind a "Menu" toggle bar on mobile) — it's a second, different navigation surface reached only inside `/minha-área`, solving a different problem (the journey map) than a page-top header, and keeps its own hamburger-equivalent toggle untouched.
