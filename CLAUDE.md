# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Avie — internal system for Fabiana Montemor's image/style consulting business. Covers the full business cycle: public lead capture via a diagnostic wizard, client CRM (Kanban), consultation scheduling, personalized report generation, and payment tracking. Deliberately minimal stack (no frontend build step, SQLite locally) so it can be maintained by non-developers.

## Commands

```bash
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt

cp .env.example .env            # set a random SECRET_KEY

flask db upgrade                # apply migrations
flask create-admin              # create a staff user; prompts for role: owner | marketing
flask seed-demo-client          # optional: idempotent fictitious client (dossiê, reports, consultations, payments) for demoing the whole system
flask run                       # http://127.0.0.1:5000

pytest                          # run all tests
pytest tests/test_basic.py::test_name   # run a single test
```

After changing `models.py`, always generate a migration instead of hand-editing the DB:
```bash
flask db migrate -m "description"
flask db upgrade
```

There is no `pytest.ini`/`pyproject.toml` — pytest runs with defaults, all tests live in `tests/test_basic.py`.

## Architecture

**App factory** (`app.py`): `create_app(config_class=Config)` builds the Flask app; a module-level `app = create_app()` exists for the gunicorn entrypoint (`app:app`, see `Procfile`). CLI commands (`create-admin`, `seed-admin`, `backup-db`) are registered via `register_cli(app)` inside the same file. `create-admin` (interactive) and `seed-admin` (non-interactive, reads `ADMIN_NAME`/`ADMIN_EMAIL`/`ADMIN_PASSWORD`/`ADMIN_ROLE` from env, idempotent, no-ops if the env vars are missing or the user already exists — used in production, see Deployment below) both set `User.role` to `owner` (full access, approves/publishes campaigns) or `marketing` (creates/edits campaigns, cannot approve).

**Extensions** (`extensions.py`): uninitialized instances (`db`, `login_manager`, `migrate`, `limiter`, `mail`) created at import time, bound to the app in `create_app`. `limiter` uses in-memory storage — fine for the current single-process deploy; switch `storage_uri` to Redis if the app ever runs multiple instances.

**Config** (`config.py`): env-driven via `.env` (`python-dotenv`). `AVIE_ENV=production` requires `SECRET_KEY` (raises at import otherwise) and turns on `SESSION_COOKIE_SECURE`. `_normalize_database_url` rewrites `postgres://` → `postgresql://` for SQLAlchemy 2.x compat (Render/Heroku/Railway hand out the old scheme) — kept as an opt-in escape hatch even though production currently runs SQLite (see Deployment). SQLite is used unless `DATABASE_URL` is set. `TestConfig` uses in-memory SQLite and disables CSRF/rate limiting.

**Blueprints** (`blueprints/`), all registered in `create_app`:
- `public` — landing (`/`), diagnostic wizard (`/diagnostico`), partial-lead capture (`/diagnostico/lead-parcial`), campaign landing pages (`/lp/<slug>`), public blog (`/blog`, `/blog/<slug>`). Has a `before_request` hook that captures `utm_*`/`gclid`/`fbclid` into the session on first touch, applied to `Client` on any subsequent form submit (`_apply_utm`).
- `auth` — login/logout.
- `dashboard` — `/painel` Kanban overview.
- `clients` — client CRUD, status transitions, consultations, payments, all under `/painel/clientes`.
- `reports` — personalized report drafting/sending.
- `campaigns` — landing page creative management under `/painel/campanhas` (see below).
- `blog` — blog post drafting/review/publish under `/painel/blog` (see below).
- `ebooks` — lead-magnet CRUD under `/painel/ebooks` (see below).
- `client_area` — the client's own self-service portal under `/minha-area` (see "Two kinds of login" below).

**Models** (`models.py`): `User` (role: `owner`/`marketing`), `Client` (+ `utm_source/medium/campaign/content/term` attribution fields), `StyleProfile`, `Consultation`, `StyleReport`, `Payment`, `Campaign`, `BlogPost`, `Ebook`. Status/choice constants (`CLIENT_STATUSES`, `CAMPAIGN_STATUSES`, `BLOG_POST_STATUSES`, `LEAD_SOURCES`, etc.) live here and are injected into every template via the `inject_globals` context processor in `app.py`, along with a `label_for(choices, key)` helper.

**Two kinds of login, one `/login` form**: `User` (staff) and `Client` both implement Flask-Login's `UserMixin` and can authenticate — they share the single `/login` route (`blueprints/auth.py`), disambiguated by a prefix in `get_id()` (`"user-{id}"` vs `"client-{id}"`, parsed back apart in `app.py`'s `user_loader`). `login()` tries `User` first, then falls back to `Client` (only succeeds if a staff member has set `Client.password_hash` — see below). Post-login redirect and which navbar renders (`templates/base.html`) both branch on the `is_staff` property (`True` on `User`, `False` on `Client`) rather than `isinstance` checks in templates. **Every internal blueprint** (`dashboard`, `clients`, `reports`, `campaigns`, `blog`, `ebooks`) registers `blueprints.auth.require_staff` as a `before_request` hook — this is the actual access-control boundary (not just `@login_required`, which a logged-in `Client` would also satisfy): it 403s any authenticated non-`User`. `client_area_bp` has the mirror-image guard (`require_client`, only in `blueprints/client_area.py`) so a `Client` can only ever reach their own data — the routes don't take a client_id param at all, they just read `current_user`.

**Client portal** (`/minha-area`, `blueprints/client_area.py` + `templates/client_area.html`): read-only self-service view of a client's own `StyleProfile` (diagnostic answers) and sent `StyleReport`s (`status="enviado"`). No self-registration — a staff member sets (or clears) `Client.password_hash` from `client_detail.html` (`clients.set_client_password`/`remove_client_password`) and relays the password out-of-band (WhatsApp/e-mail), or uses the dossiê onboarding flow below, which handles this automatically. `Client.last_login_at` is updated on every client login; the *previous* value is stashed in `session["client_previous_login_at"]` right before overwriting, so the portal can show a one-time "your last access was on X" on the very next page load — this is a lightweight stand-in for the fuller multi-entry access history the owner asked for, deliberately not built yet (needs a real spec: how many entries, what counts as an "access," etc.). "Dicas personalizadas" (personalized tips) mentioned in the same request is also not implemented — no content source for it exists yet.

**Client onboarding with dossiê** (`/painel/clientes/novo-com-dossie`, `ClientDossieForm` in `forms.py`, `clients.new_client_with_dossie`): consolidated flow for real-world clients who already received their dossiê outside the system, before Avie existed. One submission: upserts `Client` by email (creates if new, else updates name/phone on the existing record — never touches `source`/UTM attribution on an existing lead), sets `Client.status = "cliente_concluido"` (a client arriving with a finished dossiê has already been through diagnostic + consultoria, unlike `"cliente_ativo"` which implies an engagement still in progress), and upserts (not always-inserts — see `Client.dossie_report` below) a `StyleReport` with `status="enviado"`/`sent_at=now` from the submitted dossiê title, an optional `pdf_url` (external link to the original PDF, same no-upload pattern as `Ebook.file_url`), and up to five per-service fields — `estilo_pessoal`, `proporcoes`, `coloracao`, `visagismo`, `arquetipos` (each optional, at least one required). The column names predate the brand settling on final service naming; the labels actually shown everywhere are **Estilo / Biotipo / Cores / Visagismo / Arquétipos** (`blueprints/client_area.py:DOSSIE_SERVICE_LABELS`, and hardcoded in the templates/forms that touch these fields). `StyleReport.content` is auto-derived by concatenating whichever services are filled, purely so the older single-block report views (`report_view.html`) keep working. The route also generates a random temporary password (`secrets.token_urlsafe`, set via `Client.set_password` so the account is never passwordless) and a **password-reset token** (`Client.password_reset_token`/`password_reset_expires_at`, 72h validity, `generate_password_reset_token`/`password_reset_token_valid`/`clear_password_reset_token` methods) — this is the "esqueci minha senha" mechanism the client-portal note above says didn't exist yet. The reset link (`auth.reset_password`, public route, no `@login_required`) is sent via `emails.send_client_access_email` (same `MAIL_SERVER`-gated no-op pattern as everywhere else) and shown on a confirmation page (`client_dossie_success.html`) alongside a `wa.me` link built from the **client's own phone number** (normalized to digits, `55` country code prepended if missing — `clients._whatsapp_link`) with the message pre-filled, so staff can click-to-send it — this is a different `wa.me` usage than the business's own number (`config.WHATSAPP_NUMBER`) used elsewhere for inbound leads. `auth.reset_password` validates the token, logs out any current session, and lets the client set their own final password via `ResetPasswordForm`, clearing the token on success.

**One dossiê per client, editable in place** (`StyleReport.is_dossie` property — true if any of the 5 service fields is set; `Client.dossie_report` — the most recent report where `is_dossie` is true; `Client.other_reports` — everything else): `new_client_with_dossie` upserts onto `Client.dossie_report` instead of always creating a new `StyleReport`, so there's exactly one dossiê row per client and both the admin's "Dossiê" card (`client_detail.html`) and the client-area service cards always read the exact same data — editing either side is impossible; there's only one edit path, `clients.edit_dossie` (`/painel/clientes/<id>/dossie/editar`, `EditDossieForm`, same 5 services + `pdf_url`, doesn't touch client identity/credentials unlike the onboarding route). `blueprints/reports.py`'s `edit_report`/`delete_report` redirect/400 on a dossiê-type report (`report.is_dossie`) rather than letting the generic `ReportForm` — which only has `title`/`content`/`status`, no service fields — silently desync the structured data from what the client-area cards show.

**"Diagnóstico preliminar" is a separate, narrower concept from the dossiê** (`reports.new_report`/`edit_report`/`delete_report`, `client_detail.html`'s "Diagnóstico preliminar" card): this is specifically the auto-drafted report from `reports_engine.generate_report_draft(client, client.profile)`, built from the public wizard's `StyleProfile` — originally meant to help capture/nurture the lead, not to record delivered consulting services (that's the dossiê's job now). Its list only shows `client.other_reports` (dossiê-type reports are filtered out, so nothing shows twice), and each entry has its own Editar/Excluir actions.

The per-service fields exist so `client_area.index` (`blueprints/client_area.py`) can render a card per delivered service instead of the generic "Fazer meu diagnóstico" CTA — that CTA only makes sense for the public wizard funnel (`StyleProfile`, from `/diagnostico`), not for dossiê clients who already have their diagnostic embodied in the dossiê. `client_area.html`'s left card picks one of three states: `client.profile` (wizard diagnostic) → the original `dl` of answers; else non-empty dossiê service fields (`client.dossie_report`, one row now) → one card per service, each with a navy/gold circular icon badge (`.dossie-service-icon`, echoing the brand's Estilo/Biotipo/Cores/Visagismo/Arquétipos service badges) in a `.dossie-services-grid` (CSS grid, auto-fits 1–5 columns, equal-height rows); else → the CTA. The "Recomendações da consultoria" card only lists `other_reports` (same filter as the admin side), so a dossiê's content never shows twice (once as cards, once as a raw text block).

**Campaign system**: `marketing` creates a lightweight redirect page per traffic campaign — `Campaign` only has `internal_name` (panel-only label), `slug` (defines `/lp/<slug>`), `hero_title` (used for the page `<title>`, nothing else renders from it — there's no native landing page anymore, see below), and `embed_url` (the external page, e.g. a design made in Canva, that the campaign points to). Flow: `rascunho` (draft, editable) → `em_revisao` (submitted) → `publicado` (live at `/lp/<slug>`) or bounced back to `rascunho` with a `review_note`. Only `owner` can approve/reject/unpublish (`owner_required` decorator in `blueprints/campaigns.py`).

**It's a redirect, not an iframe**: the live page at `/lp/<slug>` (`blueprints/public.py:landing_campaign`) does `redirect(campaign.embed_url)` — the visitor ends up on the external page, Avie's navbar/footer are not shown there. Two earlier designs were tried and dropped: (1) a native hero section editable in Avie (title/subtitle/CTA/image/accent color, rendered by overriding parts of `landing.html`) — removed because in practice every real campaign just pointed to an external Canva design anyway, so maintaining a whole parallel hero-editing UI for a case nobody used was pure overhead; `landing.html` no longer takes a `campaign` context var at all, it only renders the fixed default hero now. (2) embedding the external page in an `<iframe>` inside `base.html` (keeping the navbar/footer) — most site builders (Canva included) block being framed from another origin via `X-Frame-Options`/CSP `frame-ancestors`, so the page silently failed to load. Redirecting is what reliably works, at the cost of leaving the Avie chrome behind on that page. `embed_url` is required in `CampaignForm` for every new/edited campaign; a pre-existing campaign saved before this field existed would have `embed_url = None` — `landing_campaign` 404s on that rather than crashing, since there's no fallback rendering left to fall back to. The campaign with `slug == "campanha"` is additionally reachable at the site root, `/campanha` (`@public_bp.route("/campanha", defaults={"slug": "campanha"})` stacked on the same `landing_campaign` view as `/lp/<slug>`) — a one-off exception for a short "main campaign" URL to hand out, requested alongside this feature. Werkzeug's `redirect_defaults` then 308-redirects `/lp/campanha` → `/campanha` automatically (avoids duplicate-content at two URLs for that one slug); every other slug only exists at `/lp/<slug>`.

**Blog system**: content-marketing funnel — articles are drafted/tested on `/blog` before being manually reused on LinkedIn. Same approval flow and `owner_required` pattern as campaigns (`blueprints/blog.py`, mirrors `blueprints/campaigns.py` almost 1:1): `rascunho` → `em_revisao` → `publicado` (live at `/blog/<slug>`, listed at `/blog`) or bounced back to `rascunho` with a `review_note`. `BlogPost.body_markdown` is authored as Markdown and rendered to HTML via the `markdown` Jinja filter (`blog_engine.render_markdown`, registered in `create_app`) — trusted staff-authored content, not sanitized beyond what the `markdown` library does by default (same trust level as other staff-supplied external URLs, e.g. `Ebook.file_url`). `blog_engine.format_date_pt` (Jinja filter `pt_date`) formats dates in Portuguese month names, since `strftime('%B')` depends on the server locale (renders in English in production). `templates/blog_post.html` is shared between the public route and the `owner_required`-free `blog.preview` admin route (`preview=True` flag, same pattern as the campaign preview). Cover images are external URLs (same ephemeral-disk reasoning as campaigns) and back `og:image` per post (`base.html`'s `{% block og_image %}`) for LinkedIn share previews. **Blog posts are subject to the same ephemeral-disk data loss as everything else** (see Deployment) — unlike ad-hoc CRM records, published articles are a real content investment, so this is worth reconsidering once the blog has real posts worth keeping.

**Ebook (lead magnet)**: `Ebook` has no approval workflow (unlike Campaign/BlogPost) — any logged-in staff creates/edits it directly under `/painel/ebooks`; `blueprints/ebooks.py`'s `activate_ebook`/`new_ebook`/`edit_ebook` enforce "only one `active=True` at a time" by flipping all others off before setting the new one. `file_url` is **always an external link** (Google Drive, Dropbox, etc.), never an uploaded file — same ephemeral-disk reasoning as Campaign/BlogPost images, but more critical here since a broken file would silently 404 for anyone who already has the link. Public flow: `GET /ebook` shows the active ebook (or a graceful placeholder if none is active — no 404) with `EbookDownloadForm`; `POST /ebook` upserts a `Client` (by email, `source="ebook"` only if the client is new — never overwrites an existing lead's original attribution), appends a note recording the download and the `wants_diagnostic` opt-in, sends the link via `emails.send_ebook_email` (same MAIL_SERVER-gated no-op pattern as `send_diagnostic_confirmation`), then redirects to `/ebook/obrigado`, which shows the download link immediately (doesn't depend on email deliverability) plus a `wa.me` link so the lead can self-initiate a WhatsApp chat — there is no automated outbound WhatsApp send, that would require a paid WhatsApp Business API not currently integrated.

**Reports** (`reports_engine.py`): `generate_report_draft(client, profile)` builds a first-pass report text from the diagnostic answers; the consultant always reviews/edits before sending. No AI/external service involved by design — the roadmap in README.md notes this as a future integration point.

**Email** (`emails.py`): `send_diagnostic_confirmation` no-ops (logs only) when `MAIL_SERVER` isn't configured, so the public form keeps working before an email provider is set up.

**Deployment**: Render.com, **free plan, zero cost** — deliberate choice while the site is experimental (see `render.yaml`). No Postgres database: production runs on SQLite same as local dev. The free plan's disk is **ephemeral** — `instance/avie.db` is wiped on every deploy and on restarts after idle spin-down, so there is no real data persistence right now; don't add features that assume production data survives across deploys without flagging that limitation. `startCommand` (`flask db upgrade && flask seed-admin && flask seed-demo-client && gunicorn app:app --bind 0.0.0.0:$PORT`) re-applies migrations, recreates the admin user from `ADMIN_*` env vars, and recreates the fictitious demo client (`seed-demo-client`, no env vars needed, always runs) on every boot, so the site is always usable again after a data wipe without a manual step. The web service (`avie-app`) was created manually, so it does **not** auto-apply `render.yaml` — its settings (plan, build/start command, env vars) must be kept in sync by hand in the Render dashboard; a `startCommand` change in this file only takes effect in production once someone pastes it into Settings → Build & Deploy → Start Command too. `.python-version` pins `3.11.9` (Render's default can be much newer and has broken `psycopg2-binary` wheels before, even though that package is currently unused at runtime). When the business justifies real cost: set `DATABASE_URL` to a Postgres connection string and switch the plan back to `starter` for a persistent disk/database.

## Frontend

No build step: Bootstrap, fonts, and the brand mark are vendored under `static/` (no CDN — the app must keep working if a visitor's network blocks Google Fonts/jsDelivr). Brand color tokens are CSS variables in `static/css/style.css`; typography in `static/css/fonts.css`. Templates extend `templates/base.html` (Jinja); form fields render via the `render_field` macro in `templates/_formhelpers.html`. The navbar's "Recursos" dropdown (Bootstrap dropdown, custom-styled dark to match the navy navbar — see `.navbar .dropdown-menu`/`.dropdown-item` in `style.css`) links to Blog and Ebook; it's duplicated with different hrefs between the authenticated branch (`blog.list_posts`/`ebooks.list_ebooks`, the admin panels) and the public `{% else %}` branch (`public.blog_index`/`public.ebook_landing`) in `base.html`.
